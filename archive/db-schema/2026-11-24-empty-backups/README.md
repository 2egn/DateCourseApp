# 빈 백업 테이블 정리 · 2026-11-24

사용자가 승인한 빈 백업 8개만 제거해 운영 테이블을 **23개에서 15개**로 정리했다. 남은 15개 테이블의 스키마와 실제 행은 모두 보존했다. 대상은 [plan.json](plan.json)의 고정 목록이며 새로 생긴 다른 백업은 포함하지 않는다. 적용·보존 검증 결과는 [cleanup-result.json](cleanup-result.json)에서 확인한다.

- `restore.sql`: 실제 `SHOW CREATE TABLE`로 보관한 빈 테이블 8개의 재생성 정의. 엔진·문자셋·인덱스를 포함한다.
- `preflight.json`: 쓰기 잠금 상태에서 0행·외래 키/뷰/트리거 참조 부재·정의 지문을 확인한 기록.
- `cleanup-result.json`: 실제 삭제와 남은 테이블의 스키마·행 보존 검사 결과. `phase=VERIFIED`가 완료 상태다.
- `postflight.json`: 새 연결의 읽기 전용 최종 확인. 테이블 15개·활성 장소 2,040곳·원본 8,179행과 카탈로그 연결 관계를 재확인했다.

<summary>처리·복원 범위</summary>

대상은 `categories_backup_*` 4개와 `data_records_backup_*` 4개다. 잠금 후 다시 빈 테이블인지 확인하고, 외래 키 검사를 끄지 않은 채 명시한 8개만 삭제한다. 나머지 테이블은 전후 DDL과 실제 행의 지문을 메모리에서 비교하며 회원 정보·저장 이미지 등 원문과 지문은 이 폴더에 저장하지 않는다.

빈 테이블 정의를 복원하려면 올바른 DB를 선택한 SQL 클라이언트에서 `restore.sql`을 실행한다. 기존 테이블을 덮어쓰는 명령이나 원본 행을 삽입하는 명령은 없다. 처음부터 0행이었으므로 복원 대상 데이터 행도 없다. MySQL DDL은 일반 트랜잭션 롤백 대상으로 간주하지 않고 보관 정의를 사용한다. [MySQL 암시적 커밋 문서](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)를 참고한다.

`ReplaceIntegratedData`의 백업 생성 기능은 유지한다. 이후 원본 교체 때 새 백업이 생기는 것은 이 정리와 별개다. 현재 원본 8,179행·카탈로그 2,040곳과 회원·코스·제보·정정·적재 이력은 삭제 대상이 아니다.
