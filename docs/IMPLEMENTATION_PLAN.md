# 구현 가능성 및 협업 설계

이 문서는 8~9주 개발, 부산 한정 출시를 기준으로 한 초기 제안입니다. 팀은 총괄을 포함한 백엔드 3명, 프론트엔드 2명으로 해석했습니다. 부산의 한두 권역부터 데이터를 검증하고 결과를 보고 지역을 확대합니다.

## 1. 사용할 기술과 구조

IntelliJ·Temurin 21·JavaFX 21·Scene Builder·Gradle은 유지합니다. DBeaver는 DB 관리, Postman은 서버 API 확인에 사용합니다. Aiven은 MySQL 호스팅이며 Java 서버의 호스팅은 별도로 필요합니다.

공유 기능을 제공하는 최종 구조는 다음과 같이 제안합니다.

```text
JavaFX/FXML 클라이언트
  ├─ Java HTTP 클라이언트 → Java REST 서버 → Aiven MySQL
  │                         ├─ 추천 엔진
  │                         ├─ 로그인·권한·저장·후기·피드백
  │                         └─ 카카오 Local API 및 허용된 공공 데이터 수집
  └─ WebView → 지도 HTML/JavaScript → 카카오 지도 SDK
```

Java REST 서버는 Spring Boot를 후보로 두고 팀의 사용 경험과 Java 21/Gradle 호환성 확인 후 버전을 고정합니다. 현재 저장소에 서버 프레임워크는 추가하지 않았습니다. 첫 추천 엔진은 순수 Java이므로 나중에 서버 모듈로 옮길 수 있습니다. 초기에는 클라이언트·서버·공통 도메인의 3개 모듈 정도면 충분하며 마이크로서비스는 필요하지 않습니다.

배포된 데스크톱 프로그램에 Aiven 계정·비밀번호나 카카오 REST 비밀 키를 포함하지 않습니다. Java 서버만 DB에 접근하고 인증·권한을 검사합니다. JavaScript 지도 키는 클라이언트에 노출되는 성격이므로 등록 도메인 제한을 적용합니다. 개발용 DBeaver 계정과 서버 실행 계정의 권한을 분리합니다. Aiven MySQL 연결은 CA를 설정하고 `VERIFY_IDENTITY` 모드로 인증서와 호스트명을 검증합니다. [Aiven TLS 문서](https://aiven.io/docs/platform/concepts/tls-ssl-certificates)

## 2. 기능 범위

| 기능 | 현실적 구현 방법 | 우선순위 |
| --- | --- | --- |
| 예산·인원·중심점·반경·카테고리 | 요청 모델 검증 및 거리 필터 | 1차 |
| 상위 3개 코스 | 후보 축소 후 조합 탐색, 예산 가지치기, 평점·거리 점수 | 1차 |
| 지도와 선택 코스 강조 | WebView에서 마커·선 표시, 선택 ID로 투명도 변경 | 1차, 선행 기술 검증 |
| 로그인·코스 저장·마이페이지 | Java 서버 인증, 사용자별 조회·수정 권한 | 2차 |
| 직접 만든 코스 | 장소 순서 편집, 저장 시 서버에서 재검증 | 2차 |
| 공유·커뮤니티·후기 | 공개 여부, 공유 ID, 코스 후기·별점 | 3차 |
| 가격 수정 요청·관리자 | 증거와 변경 이력 보관, 자동 접수 분류 | 3차 |
| 여러 사이트의 가격·평점 취합 | 데이터 사용 허용·공급원 확보 후 별도 검토 | 후순위 |
| 실제 도보·대중교통 경로 및 시간 | 별도 경로 API의 제공 범위·권한·요금·호환성 검증 | 후순위 |

첫 데모는 부산 한두 권역, 30~100개 검토된 장소, 식사·카페·문화의 3개 범주부터 시작하는 방안을 권합니다. 오락은 세부 분류 및 요금 단위가 다양하므로 다음에 추가합니다. 현재 코드는 부산 서면 주변 좌표에 놓은 가상 데이터이며 시연용 실제 데이터로 간주하지 않습니다.

## 3. 장소 및 지도 데이터

카카오 Local 검색에서 위치·이름·주소·분류를 확보할 수 있지만 공개 응답 필드에 메뉴 가격이나 평점은 없습니다. 따라서 가격·평점은 별도 공급원이 필요합니다. 식사 `FD6`, 카페 `CE7`, 문화 `CT1`을 내부 분류에 매핑하고 오락은 세부 분류/키워드와 검토된 데이터를 사용합니다. 반경 검색은 최대 20km이며 검색 결과의 노출 개수 제한도 있어 지역 전체의 장소를 빠짐없이 확보했다고 가정하면 안 됩니다. 좌표는 API의 `x=경도`, `y=위도` 순서를 내부 `latitude, longitude`로 명시적으로 변환합니다. [카카오 Local 문서](https://developers.kakao.com/docs/ko/local/dev-guide)

카카오 지도 Web SDK는 JavaScript 및 등록 도메인이 필요합니다. WebView에는 등록한 HTTP(S) 주소의 지도 페이지를 로드합니다. 개발 단계는 등록한 `http://localhost:포트`에서 지도 HTML을 제공하는 방식부터 검증하고, 배포 단계는 HTTPS 지도 페이지를 권합니다. `file://` 로딩이 동작한다고 가정하지 않습니다. [카카오 지도 가이드](https://apis.map.kakao.com/web/guide/)

지도만 HTML/JavaScript로 작성하고 후보 필터·비용·추천·저장·피드백은 Java에서 처리합니다. Java에서 JSON으로 코스 데이터를 전달하고 JS에서는 그리기만 합니다. WebView·WebEngine 조작은 JavaFX Application Thread에서 수행하고 API/DB 호출과 계산은 백그라운드 작업으로 분리합니다. [JavaFX 21 Web API](https://openjfx.io/javadoc/21/javafx.web/javafx/scene/web/package-summary.html)

첫 기술 검증의 통과 조건은 지도 로딩, 마커 3개, 원형 반경, 코스 3개의 선, 선택에 따른 강조, 키/네트워크 실패 안내입니다. 현재의 코스 거리와 선은 직선 연결이므로 실제 보행 가능한 경로로 안내하지 않습니다. WebView 호환성은 실제 JDK 21 환경에서 확인해야 합니다.

공공 데이터·사업자 제공 자료는 출처별 사용 조건, 재배포·저장 가능 범위와 갱신 주기를 확인합니다. 카카오 응답의 장기 저장·가공·공유 가능 범위도 실제 이용 조건을 확인한 뒤 수집 전략을 정합니다. 크롤링부터 대규모로 만드는 방식은 피하고 허용된 API·제공 데이터·검토된 입력 자료로 첫 지역을 구성합니다.

## 4. 비용 규칙

- 예산은 **전체 인원의 총 장소 이용 비용**으로 통일합니다. 교통비 포함 여부는 후속 요구사항이며 현재 제외합니다.
- 가격은 원 단위 정수와 하한·상한을 저장합니다. 구간 경계에서 중복되지 않도록 DB의 버킷 표기 규칙을 하나로 정합니다. 현재 데모 값은 예상 하한·상한이며 상한을 포함한 예산 검사를 합니다.
- `PER_PERSON`은 인원수만큼 곱하고 `PER_GROUP`은 한 번 더합니다. 좌석·방 수에 따라 달라지는 방탈출/노래방 등의 비용은 별도 요금 정책이 준비되기 전 추천에서 제외하거나 최대 인원을 제한합니다.
- 각 장소의 상한 합계 ≤ 총예산 조건으로 탐색합니다. 추정 상한이 실제 가격을 제한하는 것은 아니므로 예상 비용임을 표시합니다.
- 출처, 확인 일자, 가격 단위, 대표 이용 시나리오, 추정 여부, 신뢰도를 저장합니다. 확인한 가격을 이름 파싱으로 덮어쓰지 않습니다.
- 휴리스틱은 이름보다 세부 업종을 먼저 사용하고 지역별 중간값 등으로 구간을 정합니다. 단순한 전국 평균은 지역·서비스 차이를 놓칩니다. 자료가 부족하면 넓은 구간 또는 미확인 상태를 사용합니다.

## 5. 추천 알고리즘

현재 구현은 입력한 방문 카테고리의 순서를 유지합니다. 한 카테고리에 한 장소이며, 모든 장소가 중심 반경 안에 있어야 합니다. 필요 카테고리의 후보가 없으면 빈 결과를 반환하고 조건 조정을 안내합니다.

각 카테고리에서 예산·반경 조건을 만족하는 후보를 보정 평점 순으로 최대 20개 선택합니다. 최대 4개 카테고리면 조합은 최대 160,000개입니다. DFS 탐색 중 상한 예산을 넘는 분기를 제거하고 크기 3의 우선순위 큐로 결과를 유지합니다.

현재 점수는 `평균 보정 평점 - 0.15 × 직선거리(km) - 0.1 × 추정 가격 장소 비율`입니다. 평점은 `(평점×후기수 + 3.5×5)/(후기수+5)`로 보정합니다. 가중치·기준값은 임시 정책이며 사용자 반응을 보고 조정합니다. 장소 평점과 코스 평점은 별도 데이터입니다. 현재 가상 장소 평점을 사용하며, 코스 후기를 개별 장소 별점으로 복사하지 않습니다.

이 방식은 **축소된 후보 안에서 점수 기준 상위 조합**을 구합니다. 전체 장소의 전역 최적해나 최단 도보 경로를 보장하지 않습니다. 후보 축소가 저렴한 조합을 놓칠 수 있으므로 실제 데이터 단계에서는 저가 후보·거리 가까운 후보를 함께 보존하고 결과가 없을 때 범위를 넓혀 재탐색하는 정책을 추가합니다. 3개 결과가 비슷하면 공통 장소 개수에 따른 다양성 조건을 후속 적용합니다.

## 6. 서버 API 및 DB 초안

아래는 구현 예정 계약이며 현재 동작하는 HTTP endpoint가 아닙니다.

| API | 역할 |
| --- | --- |
| `POST /api/auth/register`, `POST /api/auth/login` | 계정 생성·로그인 |
| `POST /api/recommendations` | budgetWon, people, center, radiusMeters, categories → courses 최대 3개 |
| `GET /api/places` | 지도 범위 내 장소, 카테고리·페이지 조건 |
| `POST /api/courses`, `GET /api/me/courses` | 커스텀/추천 코스 저장·내 목록 |
| `GET /api/courses/{id}` | 접근 권한을 검사한 코스 상세 |
| `PATCH /api/courses/{id}` | 작성자만 편집, 공개 여부 변경 |
| `POST /api/courses/{id}/reviews` | 코스 후기 및 별점 |
| `POST /api/places/{id}/feedback` | 가격·위치 등 수정 제안 |
| `GET /api/admin/feedback`, `PATCH /api/admin/feedback/{id}` | 관리자 검토·처리 |

입력 DTO, 오류 코드, JSON 예시를 프론트엔드와 먼저 합의합니다. 서버는 클라이언트가 보낸 userId·가격·ADMIN 역할을 그대로 신뢰하지 않습니다. 로그인은 표준 비밀번호 해시 라이브러리와 만료·로그아웃 가능한 토큰 또는 세션을 사용합니다. SQL은 매개변수 바인딩, 변경은 트랜잭션으로 처리합니다.

| 테이블 | 핵심 데이터/제약 |
| --- | --- |
| `users` | ID, 유일 로그인 ID, password_hash, 표시 이름, 역할 |
| `places` | 내부 ID, 공급자+공급자 ID 유일키, 이름, 카테고리, 위도·경도, 상태 |
| `place_price_estimates` | 장소, 하한·상한, 비용 단위, 출처, 신뢰도, 확인 일자, 버전 |
| `courses` | 작성자, 제목, 인원, 예산, 공개 여부, 생성 일자 |
| `course_stops` | 코스, 순서, 장소, 저장 당시 가격 스냅샷; 코스+순서 유일키 |
| `reviews` | 작성자, 코스, 1~5 별점, 본문; 작성자+코스 유일키 |
| `place_feedback` | 작성자, 장소, 대상 필드, 제안 값, 근거, 상태, 처리 사유 |
| `place_change_history` | 변경 전후 값, 적용 버전, 처리 주체, 시각 |

좌표는 충분한 정밀도의 DECIMAL, 금액은 정수, 시간 저장은 UTC를 사용하고 표시 시 Asia/Seoul로 변환합니다. 외래키와 인덱스를 적용합니다. 장소 수정 후에도 과거 후기의 코스 구성·가격을 재현하도록 저장 시점 스냅샷을 남깁니다. 실제 SQL migration은 서버 설계와 함께 버전 관리합니다.

## 7. 피드백 자동화

처음에는 **자동 검증·분류**, 데이터가 충분해지면 제한적인 자동 반영 순서로 구현합니다.

1. 형식 검사, 음수·역전 가격·비정상 좌표 검사, 중복 요청 묶기, 계정별 빈도 제한.
2. `PENDING → AUTO_REJECTED / NEEDS_REVIEW / APPLIED` 등 명시 상태와 사유 저장.
3. 가격 급변·주소/좌표 이동·카테고리 변경·신규 계정 집중 요청은 검토 대상으로 분류.
4. 검증된 공급원이 있거나 독립적인 신뢰 계정의 근거가 일치하는 작은 수정에 한해 자동 적용 조건 검토.
5. 모든 적용은 변경 이력과 이전 버전을 보관하고 관리자에게 되돌리기 제공.

다수의 동일 요청만으로 사실이라고 확정하지 않습니다. 초기에는 신뢰도 계산의 근거가 부족하므로 가격·위치 변경을 자동으로 게시하지 않습니다. 관리자 화면은 전체 CRUD보다 피드백 큐·수정 이력·롤백을 먼저 만듭니다.

## 8. 5명 역할 분담

| 담당 | 주 책임 | 합의할 경계 |
| --- | --- | --- |
| 백엔드 1: 총괄(사용자) | 공통 모델, 추천·가격 규칙, API 계약, 통합 | RecommendationRequest/Course 및 점수 정책 |
| 백엔드 2 | 회원·인증·DB·저장/공유·후기 | 권한 규칙, 스키마 migration, 내 코스 API |
| 백엔드 3 | 장소 수집·분류·가격 추정·피드백·관리자 처리 | 장소 공급 인터페이스, 출처 및 변경 이력 |
| 프론트엔드 1 | 메인 조건 폼·추천 목록·지도 연동 | 메인 FXML, 지도 브리지, 비동기 상태 |
| 프론트엔드 2 | 로그인·마이페이지·커뮤니티·관리자 FXML | 화면 전환, 입력·오류·권한별 UI |

Scene Builder는 화면 배치 도구이며 컨트롤러의 이벤트·API 호출·상태 처리도 필요합니다. 화면 파일별 담당을 정하고 같은 FXML을 동시에 편집하지 않습니다. 컨트롤러는 추천 알고리즘이나 SQL을 포함하지 않고 서비스 호출과 표시만 담당합니다.

기능별 브랜치, 작은 PR, 공통 DTO와 `fx:id` 목록으로 협업합니다. 우선 메인 화면 담당자와 추천 담당자가 가상 데이터로 입력부터 결과 선택까지 연결하고, 나머지는 그 계약에 맞춰 서버·계정·장소 공급을 구현합니다.

## 9. 8~9주 일정과 완료 기준

1. **기술 검증:** JDK 21에서 앱 실행, Scene Builder 열기, WebView 지도 연동 및 API/DB 연결 각각 확인.
2. **핵심 데모:** 검토된 한 지역 데이터로 비용·반경·카테고리 검증, 상위 3개, 지도 선택 동기화, 결과 없음 안내.
3. **서버 연결:** 서버에서 재검증, Aiven 인증서 검증 연결, 로그인, 사용자별 저장과 조회.
4. **사용자 기능:** 직접 만든 코스 편집, 공유 권한, 커뮤니티 후기, 마이페이지.
5. **운영 기능:** 피드백 분류·처리·이력·롤백, 장애/네트워크 오류 안내, 설치 패키지.

3주차에 실제 부산 데이터 추천과 지도 연동이 완성되지 않으면 커뮤니티 확장·자동 반영을 줄여 핵심 기능을 우선합니다. 다중 사이트 평점, 정교한 자동 판정, 실제 교통 경로 계산은 이번 필수 범위에서 제외하는 제안입니다. 결정이 필요한 항목은 첫 부산 권역, Java 서버 호스팅, 이동 수단, 교통비 포함 여부, 방문 순서 편집 범위입니다. 데이터 공급 계층은 지역 코드를 받도록 확장해 지역 확대 시 알고리즘·화면을 복제하지 않습니다.
