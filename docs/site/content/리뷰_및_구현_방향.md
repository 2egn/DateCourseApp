## 유지할 사용자 흐름

사용자는 먼저 출발지·인원·전체 허용 거리를 정해요. 다음에 갈 장소의 활동·가격·이동 거리를 입력하면 후보가 최대 5곳 나오고, 그중 한 곳을 골라 코스를 이어가요. 마지막에는 순서와 조건을 확인하고 편집을 완료해요.

Java는 ‘어떤 후보가 조건에 맞는가, 거리가 제한 안인가, 금액이 얼마인가’를 계산해요. JavaScript는 그 결과를 지도에서 보여줘요. 화면이 잘 보이는 것과 계산·저장이 올바른 것을 함께 확인해야 해요.

## 먼저 해결할 문제

| 발견 사항 | 영향 | 수정 방향 |
|---|---|---|
| 도보 안내를 표시·펼치면 지도 높이가 줄어듦 | 재현 시 605px → 548px → 494px. 지도 크기 유지 원칙과 충돌 | 안내를 지도 위 고정 패널 또는 우측 메뉴로 옮기고 내부 스크롤 사용 |
| 탐색 옵션을 편집 지도에서 바꾸면 메인 경로가 이전 옵션으로 남음 | 저장 설정과 표시 경로가 불일치 | 경로 유효성에 장소 순서와 탐색 옵션을 함께 포함하고 두 지도의 이전 경로를 쓰지 않고 새 옵션으로 다시 조회 |
| 데이터 생성 안내의 스크립트가 커밋에 없음 | 같은 공공데이터를 재생성·검증하기 어려움 | 자료를 만드는 코드·입력 형식·결과 확인법을 Git에 함께 남기기 |

리뷰의 세 항목은 모두 **P2**로 보고되었다. 작업 보드 중요도는 ‘프로그램 정상 동작에 미치는 영향’으로 별도 판단한다. 탐색 옵션 불일치는 잘못된 결과 표시를 막기 위해 높음, 지도 크기 변동과 데이터 생성 절차는 보통으로 둔다.

## 구현된 것과 아직 남은 것

| 구분 | `d32bc76` 기준 상태 |
|---|---|
| 내장 지도 서버·지도 재시도 | 구현됨. 별도 Python 서버가 필요하지 않음 |
| TMAP 도보 경로 | Java 비동기 요청·이전 응답 차단·실패 표시가 구현됨. 선택적 확인 기능으로 유지 |
| 회원별 코스 저장·재조회 | 미구현. `RoutePlan` 기준으로 다음 핵심 구현 |
| 새 공공데이터 | 자료는 추가됐지만 앱 조회에 연결되지 않음. `PlaceRepository`는 기존 `integrated_places.csv` 출처를 조회 |
| 가격·평점 미상 | 현재 숫자 변환에서 미상이 0원으로 취급될 위험이 있어 모델 보완 필요 |

**무료 / 가격 미상 / 확인된 가격**을 구분한다. 메뉴 한 개의 가격도 분량이 확인되지 않았다면 1인 예상 지출로 바로 쓰지 않는다. 새 데이터 연결은 이 기준과 생성 절차가 준비된 뒤 진행한다.

## 다음 작업 순서

1. 도보 안내를 열어도 지도 크기가 바뀌지 않고, 두 지도에 같은 옵션의 길이 보이도록 고쳐요. 원래 되던 기능도 다시 확인하는 회귀 검사를 함께 해요.
2. 현재 코스 정보인 `RoutePlan`을 실제 회원별 DB에 저장하고, 목록에서 다시 열어 편집하는 흐름을 완성해요. 화면에 반영만 하는 것과 앱을 다시 켜도 남는 저장은 달라요.
3. 무료와 가격 미확인을 구분하고, 원본 자료를 다시 만드는 방법을 갖춘 뒤 새 장소 자료를 추천에 연결해요.

도보 길찾기가 실패해도 장소를 추천받고 편집을 마칠 수 있어야 해요. 관리자·커뮤니티 확장은 코스 저장·다시 불러오기가 제대로 되는 흐름을 완성한 뒤 진행해요. 현재 중요도·진행 상태는 작업 보드에서 확인하세요.

## 정리할 요소

- `RoutePlan`을 저장 기준으로 사용하고 이전 `Course`·`CoursePlace` 편집 경로는 데모·보관 대상으로 구분한다. 두 모델의 가격 기준을 섞지 않는다.
- 채택하지 않은 화면 배율 줌 실험 코드는 현재 실행 코드에서 정리하고 Git 이력으로 남긴다.
- 약 206MB의 데이터 원본·CSV·SQL·엑셀 중복을 점검한다. 생성 코드·명세·작은 표본과 큰 원본·산출물을 구분해 관리한다.
- 팀 문서 사이트는 협업 지원 작업으로 관리하고 앱 핵심 구현보다 우선하지 않는다.
