# 혼합 이동과 범위 확대 · 2026-11-17

**대중교통 선택은 장소 사이마다 실제 도보·대중교통 시간을 비교하며, 전체 범위는 이동 방법에 맞춰 확대한다.**
이 기록은 `checkpoint-2026-11-17` 이후 변경이다. 기존 태그와 당시 DB 상태 기록은 유지한다.

<details>
<summary>이동 방법과 범위</summary>

| 선택 | 출발지 중심 전체 범위 상한 | 다음 장소 반경의 정책 상한 |
|---|---:|---:|
| 도보 | 2km | 2km |
| 자동차 | 30km | 60km |
| 대중교통 + 도보 | 20km | 40km |

다음 장소 반경의 실제 상한은 현재 기준점에서 전체 원을 덮는 거리와 위 정책 상한 중 작은 값이다. 첫 장소의 상한은 전체 반경과 같다. 원의 반대편 장소 사이도 연결할 수 있도록 자동차·대중교통의 구간 상한은 전체 반경 상한의 두 배다. 모두 직선 범위이며 실제 이동거리나 시간 제한이 아니다. 기존 코스에 기록된 구간 반경은 이동 방법 변경만으로 덮어쓰지 않는다.

</details>

<details>
<summary>주요 파일·클래스와 역할</summary>

- `TravelMode`: 표시명, 이동 방법별 범위 상한, 모델의 절대 상한.
- `TransitWalkingRouteService`: 인접 장소마다 TMAP 도보와 카카오 대중교통의 전체 시간을 비교한다. 같은 시간이면 도보를 선택한다. 임의의 근거리 기준은 사용하지 않는다.
- `KakaoRouteService`: 경로 없음과 인증·통신·응답 오류를 구분한다. 명시적인 경로 없음일 때만 도보 경로로 대체하며 다른 실패는 오류로 전달한다.
- `TravelRoute.Leg.movementSummary()`: 도보·버스·지하철 순서와 시간을 Java 화면과 지도에 전달한다.
- `NextPlaceRadius`, `NextPlaceService`, `CandidateRecoveryService`: 범위를 덮는 데 필요한 상한과 확대된 후보 검색·복구 제안을 처리한다.
- `ConditionController`, `RouteEditorController`: 이동 방법 변경·초기화·저장 코스 복원 시 슬라이더와 상한 설명을 동기화한다.
- `PlaceMapPayload`, `map.js`: Java가 지도에 한계를 전달한다. 도보 단계는 점선, 탑승 단계는 실선으로 표시하며 경로 hover·클릭은 유지한다.
- `07_saved_courses.sql`, `13_expand_course_ranges.sql`, `SavedCourseRepository`: 신규 DB와 기존 DB의 전체 30km·구간 60km 저장 한계를 정의한다.

<details>
<summary>시간과 오류 처리</summary>

대중교통 응답의 접근·환승·도착 도보 단계는 그대로 유지한다. 선택된 경로의 전체 시간을 한 번 합산하며 도보 단계 시간을 다시 더하지 않는다. 도보 전용 구간은 조회된 실제 보행 경로와 안내를 사용한다. 공급사 좌표 사이에 임의의 직선을 추가하지 않는다.

비교에는 구간당 도보와 대중교통 호출이 필요하다. 인증·한도·네트워크 장애를 ‘대중교통 없음’으로 숨기지 않는다. 취소된 작업은 다음 공급사 호출 전에 중단한다. 실제 후보 추천 정렬은 여전히 직선거리 기준이다.

API 단계 타입과 상태 코드는 [카카오 공식 REST 문서](https://developers.kakao.com/docs/ko/kakaomap/rest-api)를 따른다.

<details>
<summary>검증과 운영 DB 반영 상태</summary>

공개 부산 좌표의 실제 호출에서 첫 구간 도보 10초, 다음 구간 버스→도보→지하철 2,084초를 수신했고 합계 2,094초를 확인했다. 응답 원문·인증값은 보관하지 않았으며 DB에 접근하지 않았다.

전체 Java 회귀 검사 348개가 통과했다. 혼합 선택·시간 합산·오류/취소 분리·지도 선/팝업·확대 검색/복구·이동 방법 전환/초기화·H2 저장/복원을 확인한다.

**2026-11-17 사용자 승인 후 운영 DB에 SQL 13을 적용했다.** 전체 반경 CHECK는 200~30,000m, 구간 반경 CHECK는 NULL 또는 200~60,000m로 확인했다. 적용 전후 코스·장소 행 수는 같았고 기존 데이터 행을 수정·삭제하지 않았다. 따라서 기존 2km CHECK에 의한 확대 코스 저장 차단은 해소됐다. 실제 사용자 코스를 만들어 운영 DB 저장·다시 열기를 시험하지는 않았다.

자동 승인 검토에서 처음 요구한 운영 DB 변경 승인을 사용자가 명시적으로 제공한 뒤 적용했다. 적용 전 제약 정의와 적용 후 검증 결과는 로컬 `build/version-checkpoint/range-migration-state.json`에 기록했다.

이 SQL은 두 CHECK 제약을 넓힌다. 기존 코스·장소 행을 수정하거나 삭제하지 않는다. 준비된 적용 도구는 기존 제약의 예상 형태를 먼저 확인하고 적용 전후 행 수를 비교한다. MySQL DDL은 암묵적으로 커밋되므로 적용 후 소스 태그만 바꿔도 DB 제약이 원복되지는 않는다. 새 범위의 코스가 생긴 뒤에는 기존 2km 제약으로 단순 축소할 수 없다.

</details>
