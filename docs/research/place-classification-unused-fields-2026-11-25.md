# 장소 분류 세분화와 미사용 원본 필드 검토 · 2026-11-25

기준: `8b5efe4`, 운영 카탈로그 5,628곳. [수량·원본 분류·DB 대조 근거](place-classification-unused-fields-2026-11-25.json).

이번 검토는 이미 보유한 원본·DB 값과 현재 호출 중인 API의 응답 필드를 찾는 작업이다. 거리로 점수 만들기, 후속 활동 연결성, 건물 조합 수 같은 새 지표는 범위에서 제외했다. 코드·카테고리·DB 내용을 변경하지 않았다. 운영 DB는 현재 전체 파일 쌍과 payload가 일치함을 읽기 전용으로 확인했고 `applied=false`다. 새 경로·장소 API 요청은 하지 않았으며 API 필드는 코드와 공식 응답 정의를 대조했다.

## 분류에서 먼저 고칠 부분

현재 활동은 식사 2,800·카페 2,260·문화 568곳이다. 소분류명은 `PlaceDetails.subcategory`에 보존되고 상세 필터에도 사용되지만, 원본 중분류·업종 코드는 앱에 전달되지 않는다. `PlaceFacets.subtype`은 문자열 포함 여부로 상위 묶음을 다시 정한다.

| 확인된 문제 | 근거 | 검토 방향 |
|---|---|---|
| 원본에 있는 중분류를 잃고 상위 분류를 추측 | 원본은 횟집 I20111=한식, 파스타/스테이크 I20402=서양식, 베트남식 I20501=동남아시아를 명시한다. 현재 함수에서는 이 이름들이 기타 식사로 간다. | 원본 중분류·소분류 코드와 명칭을 함께 전달하고 명시적인 분류표를 사용한다. 기존 상세 업종을 없애지 않는다. |
| 카페 내부 세분화의 실제 근거가 부족 | 현재 카페 2,260곳의 소분류는 전부 카페다. 코드의 ‘디저트 카페’ 분기는 이 카탈로그에서 쓰이지 않는다. | 카페를 상호나 위치만 보고 테마·뷰·브런치·디저트 카페로 나누지 않는다. 실제 상세 분류가 있는 원본/API 결과가 필요하다. |
| 빵·디저트가 식사에만 속함 | 빵/도넛 130·떡/한과 68·아이스크림/빙수 39, 합계 237곳이 MEAL이다. | 화면의 ‘카페·디저트’ 이용 목적에 베이커리·디저트를 포함할지 검토한다. 빵집에 좌석·커피가 있다고 추정하지 않는다. |
| 문화 분류가 데이터셋 종류에 머묾 | 공공도서관 153·박물관/미술관 23·도시공원 348·관광지 44곳이다. 공원 원문에는 PARK_SE가 있으나 앱은 도시공원으로만 묶는다. | 공원은 원문 종류(근린·어린이·수변·문화 등)를 별도 필터로 제공할 수 있다. 박물관 FCLTY_TYPE의 공립/사립/국립/대학은 운영 주체 구분이며 박물관/미술관 구분 코드가 아니다. |
| 여가·체험 자료가 현재 세 활동 밖에 있음 | 별도 LEISURE 원본 6,032건에 볼링·탁구·수상레저와 헬스장·독서실 등이 함께 있다. | 업종별 선별 기준을 정한 뒤 별도 여가·체험 또는 문화 하위 활동으로 편입할지 결정한다. 전부 문화로 바꾸지 않는다. |

현재 구내식당 42곳도 식사 후보에 포함된다. 원본에는 구내식당·뷔페 중분류가 따로 있다. 구내식당이라는 이유만으로 외부인 이용 불가를 확정하지 말고, 이 종류를 사용자에게 드러내고 선택·제외할 수 있게 하는 방향을 검토한다.

화면 분류의 검토안은 `식사 → 원본 음식 중분류 → 실제 세부 업종`, `카페·디저트 → 카페/베이커리/떡·한과/아이스크림·빙수`, `문화 → 공원/도서관/전시·관람/관광지`다. 이는 확정 변경이 아니다. 현재 세 활동을 유지하는 정리와 네 번째 활동을 도입하는 변경은 구분해야 한다. `NextPlaceCondition`과 UI·범위·필터·저장 스냅샷이 세 활동을 전제로 하므로 이름 한 곳만 바꾸는 수정은 적절하지 않다.

원본 업종과 사용자 이용 목적은 별개로 보존하는 편이 적합하다. 기존 장소 ID·저장 코스 스냅샷을 일괄 변경하지 않는다. 현재 커피 통계 보완은 `CAFE`와 원본 소분류 `카페`를 동시에 확인한다. 이 보호 조건을 유지하고 빵집의 소분류를 카페로 덮어써 커피 1잔 추정을 적용하지 않는다.

## 현재 API에서 읽지 않는 필드

새 실호출로 응답을 채집하지 않았다. 아래는 **현재 사용 중인 엔드포인트의 공식 응답 정의와 파서의 대조**이며, 모든 장소·경로에서 해당 값이 채워져 온다는 보장은 아니다.

| API | 사용하지 않는 원본 필드 | 현재 코드와 활용 가능성 |
|---|---|---|
| 카카오 장소 검색 SDK | 상세 `category_name`, 그룹 이름·코드, `phone` | 검색 목록은 이름·주소를 표시하고, 기존 장소 대조는 이름·좌표로 URL만 선택한다. 추가 분류·전화는 읽지 않는다. 동일 장소가 확인된 조회 결과에 출처를 붙여 보여줄 수 있다. 기존 `place_url`은 이미 사용하므로 미사용 목록에서 제외한다. [공식 응답](https://developers.kakao.com/docs/ko/local/dev-guide) |
| 카카오 자동차 길찾기 | `summary.fare`의 통행료·택시 추정액, 도로별 `traffic_speed`·`traffic_state`, 도로 이름·세부 구간 시간 | 현재 파서는 전체 거리·시간, 좌표와 안내문 위주다. 이미 요청한 경로에서 요금·교통 상태를 함께 표시할 여지가 있다. 택시 추정액을 자가용 운행비로 쓰거나 대중교통의 원/인 필드에 섞지 않는다. [공식 응답](https://developers.kakaomobility.com/guide/navi-api/directions) |
| TMAP 보행자 길찾기 | `turnType`, `facilityType`·`facilityName`, 도로명·분기/주변 지점 이름, 선 구간별 거리·시간 | 현재는 총거리·시간·경로 좌표와 Point 설명문만 남긴다. 시설·회전 코드에 따른 명확한 안내와 구간 정보 표시를 검토할 수 있다. 일부 의미는 설명문에도 포함될 수 있어 ‘전혀 안내되지 않는다’고 단정하지 않는다. [공식 응답·샘플](https://tmap-skopenapi.readme.io/reference/경로안내-샘플예제) |

TMAP 공식 페이지는 보행 시설 코드 표와 샘플의 일부 코드/명칭이 서로 맞지 않는다. 따라서 숫자만 하드코딩해 계단·일반 보행로를 확정하지 말고 실제 버전의 코드와 명칭을 확인해야 한다. 계단 진입·경사로 진입 같은 회전 유형은 고도·경사도나 전체 무장애 접근성을 뜻하지 않는다.

대중교통의 요금·환승 수·단계별 수단과 시간은 이미 파싱·표시한다. 이를 새 미사용 데이터로 제안하지 않는다. 도로·보행·교통 상태는 장소의 고정 속성이 아니므로 영구 장소 정보와 섞지 않는다.

Google Places는 파일럿 도구 연동이 있으나 현재 main 앱의 실시간 상세 조회에는 연결되지 않는다. 영업시간·예약·주차·반려견·접근성 같은 항목은 API가 제공할 수 있지만, 현재 보유한 값으로 세면 안 된다. 추가 필드 요청과 과금 구분이 필요하다. [Google 공식 필드 목록](https://developers.google.com/maps/documentation/places/web-service/data-fields), [상세 요청·FieldMask](https://developers.google.com/maps/documentation/places/web-service/place-details).

## 권장 순서와 코드 근거

1. 원본 중분류·업종 코드에 기반해 식사 분류의 잘못된 기타 묶음을 정리하고 디저트 237곳의 화면상 이용 목적을 검토한다.
2. 이미 DB에 있는 홈페이지와, 원본에 있는 시설 소개·운영시간·휴관일·시설 안내를 상세 정보로 연결한다.
3. 현재 카카오 검색 결과의 세부 분류·전화, 기존 경로 응답의 요금·보행시설 정보를 필요한 화면에서 활용한다.
4. 카페의 테마·좌석·뷰나 추가 여가 활동은 실제 제공 정보·업종 선별 범위가 정해진 뒤 검토한다.
