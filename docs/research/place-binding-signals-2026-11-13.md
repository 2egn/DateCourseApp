# 주소 외에 활용할 장소 연결 근거

검토일: 2026-11-13. 공식 문서와 현재 코드·CSV를 확인했다. 이번에는 인증된 장소 API를 추가 호출하거나 연결표·앱·DB를 수정하지 않았다.

**다음 개선은 주소 규칙 추가보다 전화번호·공식 지점 페이지·확인된 지도 링크를 확보하고, 서로 다른 근거로 동일 장소를 판단하는 쪽이 적합하다.** 주소는 보조 검증과 충돌 확인에 남기되, 모든 연결의 필수 조건으로 고정하지 않는다.

## 현재 자료에서 실제 사용할 수 있는 것

`data/places/pilot/seomyeon-jeonpo-2026-11-13/places.csv`를 직접 집계했다. 값이 있다는 것은 유효하거나 최신이라는 뜻은 아니다.

| 자료 | 행 수 | 전화번호 있음 | 홈페이지 있음 | 지점명 있음 |
|---|---:|---:|---:|---:|
| 식사 | 2,182 | 0 | 0 | 374 |
| 카페 | 467 | 0 | 0 | 87 |
| 문화 | 20 | 20 | 9 | 0 |
| 합계 | 2,669 | 20 | 9 | 461 |

24곳 표본에서는 문화 8곳 모두 전화번호가 있고 6곳에 홈페이지가 있다. 식당·카페 16곳에는 두 항목이 모두 없다. 따라서 전화번호 매칭만 추가하면 식당·카페의 연결률까지 곧바로 오르지는 않는다.

화지공원과 돌산공원은 같은 관리부서 전화번호를 쓴다. 홈페이지도 브랜드 대표 사이트·대학 전체 사이트·복합시설 사이트라면 개별 가게나 시설의 식별자로 충분하지 않다.

## 활용 수단과 우선순위

| 수단 | 유용한 상황 | 한계 | 우선도 |
|---|---|---|---|
| 매장 직통 전화번호 | 주소·상호 표기가 다르지만 같은 업소인지 확인 | 공통 대표번호·관리부서·번호 재사용 주의 | 높음 |
| 공식 지점 페이지·매장 코드 | 체인점, 대학·복합시설 안의 개별 시설 | 본사 도메인만 같으면 다른 지점도 같아짐 | 높음 |
| 검토자가 확인한 Google 장소 링크 | 자동 검색이 계속 틀리는 시연 장소 | 잘못 고른 링크까지 자동 검증되는 것은 아님 | 높음 |
| 카카오의 전화·지점·장소 ID | 국내 가게 검색 결과와 Google 후보 대조 | 카카오 ID와 Google ID는 다른 체계이며 결과 영구 보관 권한은 별도 | 높음 |
| 부산맛집 공공자료의 연락처·홈페이지·다국어명 | 식당·카페 원본의 식별 정보 부족 보완 | 선정 업소만 제공. 전체 상가를 덮지 않음 | 높음 |
| 공식 별칭·영문명·이전 상호 | 서로 다른 표기로 등록된 같은 가게 | AI가 임의로 만든 별칭은 근거가 아님 | 보통 |
| 업종·메뉴·외관·층수 | 후보 우선순위와 오연결 검토 보조 | 같은 메뉴·간판·브랜드가 여러 곳에 있어 단독 승인에 부적합 | 보조 |

## 1. 전화번호로 찾고 대조하기

Google Text Search (New)는 전화번호 검색을 지원한다. 국가번호와 `regionCode`를 함께 사용하는 방식을 공식 문서에서 안내한다. `places.id`만 요청해 후보 ID를 얻고, 필요한 곳만 상세 전화번호·홈페이지를 확인하는 구성이 가능하다. [전화번호 검색](https://developers.google.com/maps/documentation/places/web-service/text-search)

Google의 `nationalPhoneNumber`, `internationalPhoneNumber`, `websiteUri`는 Enterprise 필드다. 현재 Place Details Enterprise는 월 1,000건 무료 구간이지만 계정 전체 사용량과 요청 필드에 따라 청구가 달라진다. 전화번호로 검색하는 것과 상세 전화번호 필드를 받는 것은 구분해야 한다. [필드 등급](https://developers.google.com/maps/documentation/places/web-service/data-fields), [요금표](https://developers.google.com/maps/billing-and-pricing/pricing)

다음 검사에서는 문화 표본의 기존 번호를 먼저 활용할 수 있다. 다만 **직통 번호 + 호환되는 시설명·지점 근거**를 함께 확인하고, 공통 번호는 후보 검색에만 쓴다. 전화번호가 일치해도 다른 지점이라는 명확한 근거가 있으면 보류한다.

## 2. 공식 홈페이지와 지점 코드

개별 시설 페이지나 지점별 매장 코드가 있으면 주소 문자열보다 직접적인 근거가 될 수 있다. Schema.org의 `branchCode`는 매장 식별 코드이며, `LocalBusiness`에는 전화·URL·지도 링크를 표현하는 속성이 있다. `sameAs`는 대상을 식별하는 참조 페이지를 연결한다. 실제 업체 사이트에 그 정보가 있는지는 별도 확인해야 한다. [지점 코드](https://schema.org/branchCode), [업체 구조화 정보](https://schema.org/LocalBusiness), [sameAs](https://schema.org/sameAs)

판정 예시:

- 같은 브랜드 도메인 → 약한 근거. 지점 연결 승인에 부족.
- 같은 공식 지점 페이지 경로·매장 코드 → 강한 후보 근거. 다른 시설·지점과 충돌하는지 추가 확인.
- 공식 지점 페이지가 특정 지도 장소를 직접 연결 → 해당 플랫폼 ID를 얻는 데 유용.
- 같은 대학·복합문화시설 홈페이지 → 부속 박물관·미술관까지 동일 대상으로 합치지 않음.

홈페이지에서 독립적으로 확인한 정보와 Google 응답의 홈페이지 URL은 출처를 구분한다. Google의 전화·웹사이트 응답을 원본 DB에 영구 복사해도 된다고 가정하지 않는다.

## 3. 이미 쓰고 있는 카카오 검색 활용

카카오 키워드·카테고리 검색 응답에는 `id`, `place_name`, `phone`, `category_name`, `place_url`, 좌표 등이 있다. 무료 제공 쿼터가 있으며 실제 앱의 사용량은 관리 페이지에서 확인한다. [응답 필드](https://developers.kakao.com/docs/ko/local/dev-guide), [무료 쿼터](https://developers.kakao.com/docs/ko/getting-started/quota)

현재 `src/main/resources/map/map.js`의 `resolvePlaceUrl()`은 이미 검색 응답을 받지만 마지막에 상세 URL만 꺼내 반환한다. 후속 구현에서는 검증 후보 객체를 별도로 만들어 ID·전화·지점 정보를 실시간 대조에 활용할 수 있다. 현재 지도 JavaScript SDK 경로와 REST 경로의 인증 방식은 다르므로, Java에서 호출할 때 JavaScript 키를 REST 키처럼 쓰면 안 된다.

이를 ‘카카오에서 찾았으니 Google에서도 같은 곳’으로 승인하지는 않는다. 각 플랫폼 후보의 직통 전화·공식 지점 페이지·이름과 지역 등 근거를 함께 대조한다. 같은 공급자의 오래된 정보일 수도 있으므로 단순 다수결로 결정하지 않는다. 보관 조건 확인 전에는 외부 응답을 실시간 대조 용도로 다룬다.

네이버 지역 검색도 후보를 찾는 보조 수단이지만, `telephone`은 호환성용 빈 필드라고 공식 문서에 명시되어 있다. 전화 확보의 주 수단으로 삼지 않는다. [네이버 응답 명세](https://developers.naver.com/docs/serviceapi/search/local/local.md)

## 4. Google 지도 링크를 ID로 연결하는 별도 수단

Google Maps Tools Resolution API의 `resolveMapsUrls`는 Google 지도 URL을 Place ID로 바꾼다. 짧은 공유 URL도 지원하며 한 번에 최대 20개를 처리한다. `resolveNames`는 구체적인 장소명·지역을 일괄 해석하는 후보 검색 대안이다. URL 해석은 이미 확인한 장소 링크를 옮기는 데 특히 유용하다. [공식 API](https://developers.google.com/maps/ai/maps-experience-agent-tools/resolution-api)

현재 공식 안내상 두 Resolution 메서드는 IDs Only SKU로 요청 요금 0달러다. 결제 계정과 별도 Maps Experience agent tools API 활성화가 필요하다. 현재 Places API (New) 전용으로 제한한 키는 새 서비스의 활성화·키 허용 설정을 확인해야 한다. 일반 `search_places`·상세 조회까지 모두 무료라는 뜻은 아니다. 이번에는 계정 설정을 변경하거나 실호출하지 않았다. [요금과 설정](https://developers.google.com/maps/ai/maps-experience-agent-tools)

링크를 해석해 ID를 얻는 것과 우리 원본의 같은 가게임을 검증하는 것은 별개다. 시연 장소 소수는 팀원이 실제 지도 페이지를 확인하고 링크를 등록하는 방식이 현실적인 보완책이다. 지도 URL 문자열을 직접 분해해서 CID·내부 토큰을 Place ID로 오인하는 구현은 피한다.

## 5. 식당·카페에 없는 연락처는 어디서 구할까?

부산맛집정보 공공 API는 무료이며 연락처 `CNTCT_TEL`, 홈페이지 `HOMEPAGE_URL`, 콘텐츠 ID `UC_SEQ`와 다국어 이름·소개를 제공한다. 현재 식당·카페의 전화·웹사이트 공백을 보완할 후보로 적합하다. 필드는 선택 항목이고 관광 선정 업소 중심이므로 실제 채움률과 기존 장소 연결률은 실응답으로 확인해야 한다. [부산광역시 공식 데이터](https://www.data.go.kr/data/15063472/openapi.do)

공식 브랜드 매장 안내·시설 홈페이지도 활용한다. 단, 공식 사이트의 정보라고 무제한 수집·재배포 권한까지 자동으로 생기는 것은 아니다. 필요한 시연 장소의 공개 식별 근거를 확인하는 범위부터 시작한다.

사업자번호·인허가번호·공공 콘텐츠 ID는 원 출처 안에서 이력과 중복을 관리하는 데 유용하다. 현재 사용 중인 Google 장소 응답과 이들 번호의 직접 대응표를 확보한 것은 아니다. 숫자가 있다는 이유만으로 플랫폼 간 공통 ID로 취급하지 않는다.

## 다음 매칭 방식

기존 방식은 이름·주소·좌표·유형을 모두 통과해야 했다. 앞으로는 근거별 경로를 나누고, 주소가 부족해도 다른 강한 근거가 있으면 검토할 수 있게 한다.

| 근거 | 처리 방향 |
|---|---|
| 확인된 공식 지점 페이지의 지도 링크 | ID 해석 후 동일 지점 근거 확인 |
| 고유 직통 전화 일치 + 이름·지점 호환 | 강한 연결 후보. 대표번호·번호 재사용과 충돌 확인 |
| 공식 지점 페이지/코드 일치 + 이름·지역 호환 | 강한 연결 후보. 동일 건물 내 다른 시설 구분 |
| 기존 이름·주소·좌표 일치 | 지금 방식도 계속 활용 |
| 주소만 일치, 대표번호만 일치, 이름만 유사 | 자동 승인하지 않고 검토 |
| 명확히 다른 지점·시설 | 다른 약한 근거가 많아도 보류 |

방문 가능 여부는 동일성 판정 다음에 별도로 검사한다. 전화·홈페이지가 일치한다고 휴업 상태까지 해소되는 것은 아니다.

## 추천 실행 순서

1. 기존 문화 8곳의 전화·홈페이지로 비주소 근거가 얼마나 도움이 되는지 먼저 시험한다.
2. 식당·카페는 카카오 실시간 후보와 공식 사이트·부산맛집 공공자료에서 직통 연락처·지점 페이지를 확보한다.
3. 계속 애매한 시연 장소는 확인한 Google 지도 링크를 등록해 ID를 해석한다.
4. 확인된 ID와 근거 출처·확인일을 유지하고, Google 상세 정보는 필요한 시점에 조회한다.
5. 새 근거로 후보를 맞춘 뒤에도 독립 검증용 장소를 따로 남겨, 같은 표본을 반복 튜닝한 연결률과 실제 정확도를 구분한다.

주소 정규화 추가나 임의의 유사도 점수 조정보다 **식별 근거의 종류와 출처를 늘리는 작업**을 우선한다. 이번 문서는 검토 결과이며 이 경로들의 실제 연결률 개선은 아직 측정하지 않았다.
