# 장소 데이터 자가진단 · 2026-11-16

이 문서는 확대 전 386곳 기준 진단이다. 후속 구현·확대 결과는 [수영구 확대 기록](../district-expansion-2026-11-16.md)을 참고한다.

**판정: 현재 386곳의 저장·결합 일관성은 양호하다. 도메인 모델은 유지할 만하지만, 부산 전체를 현재 수집·적재 방식 그대로 일괄 확대하는 것은 보류한다.**
현재 영업 여부나 모든 장소의 지도 동일성을 새로 실사한 결과는 아니다. 운영 DB는 SELECT로만 확인했고 수정하지 않았다.

| 질문 | 진단 |
|---|---|
| 일관되게 수집됐나? | 현재 파일·속성 팩·DB 386건이 일치한다. 원본 기준일과 계산일도 주로 분리되어 있다. 별도 수동 시설 자료의 확인일 처리에는 예외가 있다. |
| 잘못된 데이터가 있나? | 활성 표본의 ID·이름·주소·좌표 형식 오류는 발견하지 못했다. 근접 동명 3쌍은 검토가 필요하다. 원본에는 좌표 누락 6건과 중복 의심 기록이 있다. |
| 부산 전체로 확대해도 되나? | 모델의 근거·미확인·정정 분리는 활용한다. 동일 장소 연결, 추정 가격, 구별 자료 수집, 지역 조회 및 전체 스냅샷 발행부터 보완한다. |

<summary>검증 범위와 결과</summary>

- 활성 표본: 식사 240·카페 120·문화 26, 총 386곳. 출발지 중심 2km의 서면 표본이다.
- 파일 검사: ID 중복, 빈 이름·주소, 누락·비정상 좌표, 넓은 부산 좌표 상자 밖의 좌표가 없었다. 행정구역 경계나 실제 건물 위치까지 검증한 것은 아니다.
- DB 대조: 활성 386 / 기대 386 / 내용 불일치 0 / SHA-256 불일치 0 / 누락 0. 파일·속성 팩을 결합한 모델의 정규화 payload와 비교했다.
- 가격 근거: 유사 유형 추정 265·공공 기준값 2·미확인 119. 미확인 값을 무료로 대체하지 않는다. Google 검증 가격을 새로 확보한 것은 아니다.
- 과거 동일성 확인일 및 Google ID가 기록된 장소는 11곳이다. 전체 386곳의 현재 영업·지도 동일성 확인을 의미하지 않는다. 현행 로더는 과거 ID만으로 외부 연결을 승인하지 않는다.
- 이번 재실행: Python 수집/생성 관련 12개, Java 모델/속성/필터/카탈로그 29개 모두 통과. 전체 테스트를 재실행한 결과는 아니다.
- 이전 확대 때 기존 127곳의 ID·좌표·가격 및 저장 코스·제보·정정 보존을 확인했다. 이번에는 운영 변경 없이 현재 내용만 대조했다.

<summary>데이터 오류·검토 대상</summary>

**1. 활성 표본의 근접 동명 3쌍 — 중복 확정 아님**

| 이름 | 거리 | 서로 다른 도로명 주소 |
|---|---:|---|
| 청년어부 | 약 40m | 서전로10번길 18 / 13 |
| 5일장터 | 약 18m | 동천로95번길 20-5 / 서전로 14 |
| 넘버나인한우 | 약 25m | 서전로 11 / 동천로107번길 25 |

서로 다른 공공 ID이고 전화번호가 비어 있다. 이전·중복 등록·별도 업소 중 어느 경우인지 지도·공식 안내·제보 검토로 판단해야 한다. 자동 삭제나 병합은 하지 않았다. 같은 이름의 전포2-1재개발공원 2개 기록도 서로 다른 지번·좌표이며 실제 시설 단위는 별도 확인 대상이다.

**2. 원본 전체 — 정제 후 사용 필요**

- 158,347행 중 현행 모델 대상인 식사·카페·문화는 45,476행이다. 나머지 업종을 그대로 넣을 수 없다.
- 도서관 좌표 누락 6건: LIB:158·159·160·209·210·211. 현재 386곳에는 없다.
- 이름·주소를 정규화하면 같은 이름+주소 그룹이 전체 1,539개, 현행 대상 업종을 하나 이상 포함하는 그룹이 424개다. 공동 입점/복수 등록을 포함할 수 있어 모두 중복 오류라는 뜻은 아니다.
- 대상 업종을 하나 이상 포함하는 근접 동명 쌍은 670쌍이다. 50m는 검토 후보를 찾는 기준이며 동일 장소 판정 기준이 아니다. 같은 이름이 150행을 넘는 그룹은 쌍 탐색에서 제외했으므로 전수 쌍 개수가 아니다.
- 전화 936/45,476·웹사이트 215/45,476로 보조 식별 근거가 부족하다. 원본 CULTURE 1,051행 중 45행은 기준일이 2024년 이전이다.

**3. 시간 근거와 파일 검증 — 확인된 처리 문제**

- `collect_busan_appeal_data.py:collect`는 박물관 무료 관람/오디오가이드의 수동 근거를 코드로 추가하면서 `checkedAt=DATE`를 사용한다. `--offline`도 같은 날짜를 기록하므로 실제 재확인 없이 확인일이 새로 보일 수 있다. 이 별도 `additional_facility_facts.json`은 현재 앱에 자동 반영되지 않는다. 최초 수동 확인일을 보존하고 생성일을 분리해야 한다.
- 원본 SQL은 Git의 LF 바이트가 manifest 해시와 일치하지만 Windows 작업 파일은 CRLF라 바이트 해시가 다르다. 내용 훼손은 아니며, LF 정규화 시 일치한다. 해당 SQL의 LF 규칙을 고정할 필요가 있다. 현재 앱의 JSON/속성 팩 지문은 통과했다.
- 역 원본 135행 중 118행은 2022년 기준이다. 2026년 계산일이 최신 역 정보를 뜻하지 않는다. 버스/역 근접도는 직선거리이며 출입구·실제 보행 접근성을 보장하지 않는다.

<summary>가격·어필 태그의 추천 품질</summary>

가격 계산은 메뉴 행 수가 많은 가게에 치우치지 않도록 **장소별 메뉴 중앙값 → 장소 간 평균**을 사용한다. 다만 표본 자체가 착한가격업소이므로 일반 업소에 적용하면 낮게 추정할 수 있다.

| 추정 그룹 | 장소 표본 수 | 현재 추정액 |
|---|---:|---:|
| 한식 | 115 | 7,000원 |
| 카페 | 25 | 2,400원 |
| 중식 | 57 | 6,000원 |
| 일식 | 5 | 8,200원 |

특히 일식 5곳의 넓은 그룹 평균이 `일식 회/초밥` 31곳에도 적용된다. 중국집과 마라탕/훠궈 역시 같은 그룹이다. 개별 매장 가격이 틀렸다고 입증한 것은 아니지만, 예산 추천에는 약한 근거다. 메뉴/업종 단위를 좁히고, 표본이 부족하면 미확인 유지 또는 추정 범위를 사용해야 한다. 표본 수·집계 방식·대상 업종을 설명 문자열 외의 구조화된 근거로 보관하면 갱신과 검증이 쉬워진다.

지정 태그는 상호+도로명 건물번호의 유일 일치를 쓰고 모호한 연결은 검토 목록으로 보낸다. 이 보수적 원칙은 유지할 만하다. 다만 모범음식점은 현재 부산진구 자료만 사용한다. 다른 구의 태그 부재는 미지정을 뜻하지 않는다.

역 500m 태그 368/386, 버스 200m 태그 385/386으로 서면에서는 대부분 해당한다. 데이터 계산 오류의 증거는 아니지만 추천을 구별하는 힘은 작다. 가까운 거리 자체를 보조 정보로 사용하거나 선택 기준을 조절할 수 있다.

<summary>오프라인 규모 시험과 한계</summary>

실제 원본 좌표·ID·주소와 현재 모델의 속성/가격 템플릿을 재표본화한 비용 시험이다. 시험 자료를 DB에 넣거나 실제 장소 사실로 채택하지 않았다. 현 PC JVM에서 5회 예열 후 서면 반경 2km의 식사·카페·문화 검색 30회를 측정했다.

| 건수 | JSON 크기 | 전체 JSON 복원 | 메모리 검색 중앙값 / P95 |
|---|---:|---:|---:|
| 386 | 약 1.0MB | 약 40ms | 0.35 / 1.08ms |
| 5,000 | 약 9.5MB | 약 138ms | 0.41 / 1.72ms |
| 45,470 | 약 86.4MB | 약 392ms | 1.92 / 8.54ms |

단일 실행의 대략적인 비용이다. JSON 크기는 DB/힙 사용량과 다르다. DB 전송·접속·해시 검사·적재 트랜잭션·속성 수집·지도 마커·UI 렌더링·동시 사용을 포함하지 않는다. 검색 계산만으로 확장 불가라고 볼 근거는 없지만 이 수치로 도시 전체 운영을 보장할 수는 없다.

이번 진단 스크립트와 상세 결과는 로컬 `build/data-self-audit/`에 있다. build는 임시 산출물이며 Git에 포함하지 않는다.
