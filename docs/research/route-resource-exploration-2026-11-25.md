# 현재 보유 자원으로 가능한 경로 추천 개선 · 2026-11-25

코드 기준 `5ecb907`과 부산 전역 후보 5,628곳을 검토했다. 장소의 운영 적재 결과는 별도 보고서로 구분하며 이 문서의 실험은 DB·공급사 API를 사용하지 않는다. 아래 개선안은 앱에 구현한 기능이 아니다.

현재 편집 화면은 `CourseEditorController.onRecommendNext` → `NextPlaceService.matching`으로 전체/구간 직선 반경, 가격·미확인 포함 여부, 활동·세부 업종·특징, 중복 제외를 적용한 뒤 직선 거리순으로 후보를 보여준다. 실제 도로 이동시간이 후보 순위를 정하는 구조는 아니다. `PlaceSearchService.recommend`의 별도 가격 중심 추천과 현재 편집 화면의 호출 경로를 혼동하지 않는다.

| 우선순위·요소 | 현재 자원·활용 상태 | 활용 제안·제약 |
|---|---|---|

구간별로 도보와 대중교통 중 빠른 결과를 선택하는 `TransitWalkingRouteService`는 이미 구현돼 있다. 위 실제 이동 부담 제안은 이 기능을 새로 만든다는 뜻이 아니라, 조회 결과를 제한된 후보 비교에도 활용할지 검토하는 것이다. 주차·주차 후 도보·체류시간은 현재 자동차 이동시간에 포함되지 않는다.

`ExternalPlaceSnapshot`에는 영업 구간·외부 평점 등의 임시 모델이 있지만 현재 main 코드에 실제 조회·추천 연결은 없다. 모델이 있다는 이유로 확보된 실시간 자원으로 세지 않는다. 후보의 평점은 모두 0이며 미확인 표시용 값이지 낮은 평점이 아니다. 평점·리뷰 수·날씨·고도/경사·혼잡도·실제 방문/선호 학습 기록은 현재 자원으로 추천 점수에 쓸 수 없다. 저장 코스는 실제 방문·만족의 증거가 아니다.

## 기존 모델로 한 탐색 실험

- 동일한 696개 오프라인 조건, 같은 반경·가격·미확인 규칙을 유지했다.
- 원래 가장 가까운 장소 하나씩 선택하면 세 활동이 완성된 조건은 535개다.
- 그중 끊긴 161개 조건에서 단계별 가까운 후보 최대 5곳까지만 되짚어 비교했다.
- 19개 조건에서 세 활동을 이을 수 있는 대안을 찾았다. 기존 535개를 유지하면 대안이 존재하는 조건은 합계 554개다.
- 고정된 식사→카페→문화 순서의 제한된 탐색이다. 최적 경로·최단 실제 시간·이용자 완료율·개인화 성능 검증이 아니며, 나머지 조건에서 가능한 코스가 전혀 없다는 뜻도 아니다.

재현 도구는 `tools/catalog-ops/RouteResourceProbe.java`, 상세 입력 SHA와 예시는 [실험 결과](route-resource-lookahead-2026-11-25.json), 자료별 수량과 원문 운영시간 연결은 [자원 목록](route-resource-inventory-2026-11-25.json)에 있다. 기존 전체 Java 398개·보관 2개와 실험 실행을 통과했다. 실제 경로 공급사 호출·운영 DB 변경은 이 실험에서 수행하지 않았다.

```powershell
$catalogPack = 'data/places/expansion/busan-balanced-2026-11-25'
.\gradlew.bat -I tools/catalog-ops/verify.init.gradle exploreCatalogRoutes "-PplaceDataset=$catalogPack/places.json" "-PplaceFacts=$catalogPack/appeal/demo_appeal_facts.json" "-PplaceRehearsal=$catalogPack/rehearsal-report.json" "-PplaceScenarios=$catalogPack/rehearsal-scenarios.json" '-PplaceReport=build/route-resource-lookahead.json' --offline --no-daemon
```
