# 편집 중 예상 이동 시간 누적 검토

상태: **검토만 진행. 자동 누적 기능은 아직 구현하지 않음.** 현재 편집 화면의 도보 경로 버튼으로 수동 계산은 가능하다. 사용자 요청일: 2026-11-14.

## 추천 방향

먼저 **장소를 추가한 뒤 새 구간 하나만 계산하고, 코스의 이동 시간을 합산**한다. 후보 5곳 비교는 두 번째 단계로 둔다. 과제의 남은 일정과 반복 추천 시 호출 수를 고려한 제안이다.

```text
출발 → 장소 A: 계산 결과 유지
장소 A → 장소 B: 새로 추가한 이 구간만 조회
예상 이동 시간 = 두 구간 소요 시간의 합
```

| 방식 | 확인할 수 있는 시점 | 추가 요청량의 예 | 우선순위 |
|---|---|---|---|
| 장소 추가 후 새 구간 계산 | 선택 직후 누적 시간 | 새 구간당 1회 | 먼저 구현 |
| 후보 5곳의 직전 장소→후보 계산 | 선택 전에 각 후보 비교 | 추천 1회에 최대 5구간 | 이후 검토 |

위 요청량은 한 구간을 한 번씩 조회하는 구성 기준이다. 재추천·조건 변경·순서 변경 때 다시 필요한 요청은 별도다. 같은 출발·도착·탐색 옵션의 유효한 결과가 있으면 재사용한다. 실제 API 응답 시간이나 계정의 남은 호출량은 이번 검토에서 측정하지 않았다.

## 표시 제안

- `예상 이동 24분 · 3구간`: 계산이 끝난 경우.
- `확인된 이동 18분 · 1구간 계산 중`: 일부만 끝난 경우.
- `확인된 이동 18분 · 1구간 미확인`: 실패한 구간이 있는 경우. 실패를 0분으로 합산하지 않는다.
- 후보에는 추후 `이전 장소에서 도보 약 7분`을 표시한다. 장소 자체의 방문 시간으로 표시하지 않는다.

**이동 시간과 머무는 시간을 구분한다.** 식사·관람 시간은 길찾기 API가 알려 주지 않으므로 이동 시간만으로 ‘전체 데이트 소요 시간’이라고 표시하지 않는다. 머무는 시간은 나중에 사용자가 입력하거나 별도 가정값임을 표시하는 범위로 검토한다.

## 구현할 때 필요한 처리

1. 코스 편집의 장소 추가 이벤트에서 새 마지막 구간을 계산한다. 진행 중에도 장소 추가·삭제를 허용할 수 있도록 구간별 계산 상태를 둔다.
2. 출발·도착 좌표와 탐색 옵션을 기준으로 앱 메모리에서 재사용한다. TMAP 결과를 영구 장소 DB에 적재하는 기능으로 만들지 않는다. 제공자의 결과 사용 기한도 지킨다.
3. 삭제·순서 변경 시 바뀐 구간만 무효화한다. 예를 들어 A→B→C에서 B를 지우면 A→C가 새로 필요하다.
4. 코스 초기화·다른 코스 열기·옵션 변경 후 도착한 이전 응답이 현재 합계를 덮어쓰지 않도록 버전으로 구분한다.
5. 편집 완료 후 지도 경로를 계산할 때 이미 유효한 구간 결과는 재사용해 중복 요청을 줄인다.

후보 5곳 조회를 구현한다면 동시에 무제한 요청하지 않고 대기열·취소·실패 표시를 둔다. 계산이 덜 끝난 후보를 숨기거나 임의의 짧은 시간으로 정렬하지 않는다. 현재의 최대 5곳 선정 알고리즘을 실제 이동 시간 기반으로 바꾸는 것은 별도 결정이다.

현재 읽을 코드는 `RouteEditorController.onAddCandidate()`, `PlannerMap.currentWalkingStops()`, `WalkingRouteService`, `WalkingRoute.Leg`다. 기존 `WalkingRoute`는 거리·초 단위 시간을 이미 보관하지만, 편집 요약의 구간별 상태·재사용·자동 합산 연결은 아직 없다.
