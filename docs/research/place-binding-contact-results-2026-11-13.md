|---|---:|---:|---:|
| 이번에 검사한 문화시설 8곳 | 2 | 4 | 2 |

이전 판정은 8·15·1이었다. 단순히 연결률을 크게 올린 결과가 아니라, 다른 식별 근거로 추가 연결 1곳과 휴관 제외 1곳을 확보했다. 이번 표본을 보고 보정했으므로 독립적인 정확도 검증은 아니다.

## 주소 없이 무엇으로 연결했나?

`contacts.py → assess()`에 다음 경로를 추가했다.

1. 자료 안에서 공유되지 않는 전화번호 + 호환되는 이름·지점 + 시설 유형·대략적 위치.
2. 공식 출처에서 같은 시설임을 확인한 개별 홈페이지 + 호환되는 이름·유형·대략적 위치.
3. 이름이 다를 때는 고유 전화와 확인된 개별 시설 페이지가 모두 맞아야 하며, 다른 지점이나 상위 복합시설로 합치지 않는다.

이 경로에서는 주소 문자열 일치를 요구하지 않는다. 위치는 같은 지역인지 확인하는 500m 보조 한도로 사용하며 주소를 다시 만드는 수단으로 쓰지 않는다. 시설 이름·유형이 다르거나 명확한 연락처 충돌이 남아 있으면 보류한다.

공원 두 곳의 같은 관리부서 전화는 고유 번호로 취급하지 않았다. 공통 전화로 재검색하지도 않았다. 회사 전체 홈페이지·대학 메인·검증하지 않은 개별 URL만으로 승인하지 않는다. 원본의 범천 홈페이지가 실제 다른 시설인 사례가 그 이유다.

홈페이지 확인은 사람이 공식 페이지의 시설명을 대조해 보정 파일에 기록한 이번 세 곳의 검증이다. 모든 웹사이트 내용을 자동으로 읽고 시설명을 확인하는 기능을 만든 것은 아니다.

## 검증 과정과 호출량

- 첫 대조: 상세 8회 + 전화번호 검색 5회 = 13회. 신규 자동 연결은 없고, 기존 도서관 한 곳의 연락처 차이가 발견됨.
- 공식 안내 검토: 공개 시설 페이지 확인. 별도 인증키 불필요.
- 출처 보정 뒤 재대조: 세 곳의 기존 Google 후보를 상세 3회 조회.
- **이번 Google 요청 합계 16회.** 가격·평점·리뷰는 요청하지 않았다. 계정 청구액은 확인하지 않았다.

전화번호 검색 5회에서 추가 후보를 확보하지 못했다. 연락처가 있다고 항상 검색되는 것은 아니다. 원본의 잘못된 연락처를 그대로 검색하면 도움이 제한된다는 것을 이번 표본에서 확인했다.

Google 응답 본문·전화·웹사이트 원문은 파일로 보관하지 않고 ID와 자체 판정·근거 여부만 남겼다. 공개 공식 페이지에서 확인한 보정값은 출처를 따로 기록했다.

## 파일 찾기

자료 폴더: `data/places/pilot/seomyeon-jeonpo-2026-11-13/`

| 파일 | 역할 |
|---|---|
| `google-contact-evaluation-v4.json` | 보정 전 전화·홈페이지 대조의 중간 판정 |
| `contact-source-overrides.json` | 공식 출처에서 확인한 세 시설의 연락처·홈페이지·휴관 보정 |
| `google-contact-reconciled-v5.json` | 보정 후 세 곳 재대조와 전체 판정 |
| **`google-bindings-v5.json`** | **현재 Java 데모에서 읽는 9곳 연결표** |
| `binding-review-v5.csv` | 검토 13곳과 방문 제외 2곳을 한국어로 정리 |

기존 v1~v3 연결표와 원본 CSV는 그대로 있다. v5 연결표에는 CSV 해시뿐 아니라 공식 보정 파일의 해시도 있다. 두 파일 중 하나라도 달라지면 Java 조회기가 재검증 오류를 반환한다.

## 실행 확인과 코드 읽기

프로젝트 최상단에서 실행한다. 아래 두 명령은 실제 API·DB를 호출하지 않는다.

```powershell
.\gradlew.bat runPlaceBindingDemo
python -m unittest discover -s tools/place-data-pilot -p "test_*.py" -v
```

데모: 연결 9곳, 범천도서관 true, 휴관 중 부전도서관 false. 기존 앱 `CAFE_0464`는 여전히 미연결이다. 외부 정보가 실제 추천·상세 화면에 표시되는 단계는 아니다.

읽는 순서:

1. `contacts.py → phone_key / website_key`: 국가번호·내선 처리, 지점 식별에 필요한 URL 경로·쿼리 보존.
2. `assess`: 전화·확인된 홈페이지 기반 판정. 원본 공유 번호와 영업 가능 여부를 별도 처리.
3. `apply_overrides`: 원본 사전값이 맞을 때만 별도 출처 보정을 적용. CSV 객체는 복사해 사용.
4. `reconcile`: 공식 보정 세 곳을 재대조하고 최신 연결표 생성.
5. Java `PlaceBindingCatalog.load`: 연결표 버전·CSV·공식 보정 파일의 해시를 검증한 뒤 읽기.

실제 호출 명령 `contacts.py live`, `contacts.py reconcile`은 이미 실행했다. 잠금 파일·결과 파일을 유지해 실수로 재호출하거나 이전 결과를 덮어쓰지 않게 했다.

## 다음 방향

이번에는 문화 8곳만 검사했고, 식당·카페는 연락처·홈페이지가 비어 있어 적용하지 않았다. 다음 단계는 카카오 검색·공식 매장 페이지·부산맛집 공공자료에서 식당·카페의 식별 근거를 확보하는 것이다. 번호나 URL이 채워졌다고 바로 승인하지 말고 시설명·지점과 출처를 함께 확인한다.

연결의 동일성, 연락처의 최신성, 실제 방문 가능 여부를 별도 상태로 다루는 것이 중요하다. 한 값이 충돌하면 공식 출처를 대조할 수 있게 남기고, 필요한 장소만 소규모로 검증하는 방향이 과제 범위에 맞다.
