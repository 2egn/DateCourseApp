# DateCourseApp 다방면 리뷰 — 2026-11-15

## 범위와 검증

통합 실행 경로 AppLauncher → MembershipApp → ConditionController/RouteEditorController,
장소 추천/식별/가격 모델, 저장 코스와 프리뷰, 사용자 세션 캐시, 제보/관리자 검토,
지도 서버와 백그라운드 작업, 빌드/테스트/문서를 검토했다.
앱 기능은 수정하지 않았다. 소스 검토와 기존 FXML 렌더링 시안을 사용했고,
현재 `./gradlew test jar` 성공 상태를 확인했다(300개 일반 테스트; 이번 호출은 up-to-date).
직전 실제 지도 테스트 2개도 성공 결과가 남아 있다. 이번 리뷰에서 신규 회원 가입,
실제 사용자 코스 변경, 관리자 운영 데이터 변경은 수행하지 않았다.

장소 동일성 불일치는 `build/review/ReviewProbe.java`를 별도 컴파일/실행해 재현했다.
운영 데이터가 아닌 합성 장소를 사용했다. 앱 전체를 새로 수동 조작한 UX 평가나
모든 운영 장애 조건의 재현으로 확대 해석하지 않는다.

## 우선 발견 사항

### 1. [P1] 창 닫기가 미저장 코스 확인을 우회한다

근거: `MembershipApp.java:75`는 JFrame.EXIT_ON_CLOSE를 설정한다.
파일 전체에 windowClosing 등 플래너의 미저장 확인을 호출하는 핸들러가 없다.
반면 `ConditionController.java:427`의 hasUnsavedChanges는 로그아웃/코스 교체에 쓰인다.

재현 조건: 코스를 편집하거나 새 코스를 구성한 뒤 저장하지 않고 메인 창의 X를 누른다.
결과: 저장 여부 확인 없이 프로세스가 종료돼 초안과 미저장 확정 코스가 사라진다.
저장 작업 자체가 진행 중일 때도 종료를 막는 흐름이 없다.
권장: 공통 종료 요청 경로를 만들고 Swing 창 닫기에서 JavaFX 상태 확인을 거친다.
저장 중 종료와 미저장 변경을 구분하고 취소하면 현재 화면으로 돌아오게 한다.

### 2. [P2] 추천과 도메인 모델이 서로 다른 장소 동일성 규칙을 사용한다

근거: `Place.java:31`의 sameIdentityAs는 public ID를 우선하며 서로 다른 public ID를
이름/좌표만으로 합치지 않는다. `PlaceSearchService.java:32`는 placeId 또는 이름+좌표로
합치고, `:94`의 identity는 public ID를 보지 않는다. NextPlaceService는 이 추천 결과에
다시 sameIdentityAs를 적용한다.

별도 실행 결과:
- 서로 다른 public ID, 같은 provider ID/이름/좌표: 모델은 다른 장소(false), 후보는 1개.
- 같은 public ID, 다른 provider ID/약간 다른 좌표: 모델은 같은 장소(true), 후보는 2개.

영향: 원본/매칭 데이터가 병합될 때 별개의 장소가 누락되거나 같은 장소가 여러 후보로
노출될 수 있다. 현재 운영 127곳에서 해당 조합이 이미 발생했다고 단정하지 않는다.
권장: 도메인 동일성 규칙을 한 곳으로 모으고 추천·이미 선택된 장소 제외·저장 검증에서
공유한다. 공공 ID가 다른 경우와 외부 ID가 바뀐 경우를 함께 회귀 검사한다.

### 3. [P2] 프리뷰 재생성 실패가 기존의 유효한 이미지까지 삭제한다

근거: `SavedCourseRepository.java:224` replacePreview는 기존 이미지를 먼저 DELETE하고,
png == null이면 그대로 반환한다. 같은 내용 재저장에도 적용된다.

재현 조건: 정상 프리뷰가 있는 코스를 변경 없이 다시 저장하는데 지도 캡처에 실패한다.
결과: 코스 저장은 성공하지만 기존 정상 프리뷰도 없어진다. 현재 테스트에도 렌더러 실패 시
기존 이미지 삭제를 기대하는 검사가 있어, 테스트 통과와 원하는 복구 동작은 별개다.
권장: 저장 내용 해시가 같으면 기존 이미지를 유지하고, 내용이 바뀌어 해시가 달라진
이미지만 무효화한다. 이미지 재생성을 코스 수정과 독립적으로 재시도할 방법도 검토한다.

### 4. [P2] 제보가 누적되면 오래된 미검토 건을 화면에서 찾을 수 없다

근거: `InformationReportRepository.java:69`는 상태 구분 없이 최신 300건만 조회한다.
`InformationReviewController.java:31`의 화면에는 다음 페이지나 미검토 전용 조회가 없다.

조건: 어떤 미검토 건 뒤로 제보가 300건 이상 접수된다.
결과: 해당 미검토 건은 DB에 남아 있지만 현재 관리자 UI 목록에서 사라진다.
권장: 미검토 건 우선 큐와 상태별 필터, ID 기반 페이지 조회를 제공한다.
시연 데이터 정정 방안이 운영 흐름으로 계속 작동하려면 필요한 부분이다.

### 5. [P2/실행 환경] 8080 포트 충돌이 지도 전체를 막는다

근거: `MapPageServer.java:23`은 고정 8080 포트에 서버를 열고, 생성 실패 시 지도를 로드하지
못한다. PlannerMap은 오류 안내/재시도는 제공하지만 포트 점유를 해소하는 기능은 없다.

조건: 다른 개발 서버가 8080을 사용하거나 앱을 두 번 실행한다.
영향: 지도 검색·편집·이미지 캡처를 함께 사용할 수 없어진다.
권장: 단일 실행 제어와 시작 단계 충돌 안내를 우선 검토한다. 대체 포트 사용은
현재 지도 키의 허용 도메인 설정과 함께 검증해야 하므로 임의 포트 변경만으로 해결하지 않는다.
이번 리뷰에서 사용자의 기존 실행 프로세스는 종료하지 않았다.

### 6. [P3] README의 실행 상태 설명이 현재 코드와 다르다

README는 관리자 인증이 동작하지 않는다고 설명하지만 현재 MemberRepository.login은
AdminSession을 발급하고 MembershipApp이 관리자 창으로 연결한다. 후보 최대 5개,
선택한 장소 추가 버튼, 화면 슬라이드 등도 최근 구현과 다르다. 실제 DB 적용/검증이
전혀 없다는 오래된 문구도 있어 팀원이 현재 상태를 오해할 수 있다.
권장: 통합 앱의 현재 동작과 별도 데모/미완성 화면을 구분해 문서화하고 실행 경로를 정리한다.

## UX와 정보 표현

좋은 점:
- 공통 조건 → 장소별 선택 → 편집 완료 → 저장의 중심 흐름이 정리돼 있다.
- 확정 코스와 편집본을 분리하고, 빈 후보에 조건 완화 선택지를 제공한다.
- 참고/추정/미확인 가격을 구분하며 가격 미확인을 무료로 계산하지 않는다.
- 저장 화면은 지도에 남는 공간을 배정하고 장소 목록을 작게 제한한다.
- 후보 선택의 상세 정보가 지도 핀과 연결되고, 필터 그룹/선택 칩을 제공한다.

추가 검토:
- 저장 대기 중 현재 단계(지도 준비/이미지 생성/DB 저장)를 구분하면 오래 기다리는 이유가 명확하다.
- 프리뷰 실패 안내에 구체적인 재시도 동작을 붙이면 사용자가 코스 전체를 다시 저장하지 않아도 된다.
- 지도 로딩 실패, 도보 API 실패, DB 실패의 재시도 동작과 설명을 구분한다.
- 키보드만으로 핀/장소 선택 → 상세 → 코스 추가 흐름을 끝낼 수 있는지는 실제 수동 검증이 필요하다.
- 긴 상호/주소, 높은 Windows 배율, 좁은 창, 다중 모니터에서 추가 화면 검증을 권한다.
  현재 시안만으로 이 환경들이 모두 검증됐다고 보지 않는다.

## 객체지향과 유지보수

좋은 기반은 불변 RoutePlan/Place/PriceEstimate, UI와 분리된 추천/반경 서비스,
Repository 경계, 세션별 UserContext 캐시, PlacePresenter/SavedCoursePresenter다.
일반 폼 베이스 클래스에 모든 상태를 모으는 방향보다 현재의 역할 분리를 유지하는 편이 낫다.

현재 크기: ConditionController 712줄, RouteEditorController 715줄, PlannerMap 418줄,
map.js 1294줄. 줄 수만으로 문제라고 보지는 않지만 화면 전환·데이터 조회·편집 상태·
저장/캡처·경로 상태가 함께 바뀌어 변경 범위를 파악하기 어렵다.

작은 단계의 분리 권장:
1. 장소 동일성을 도메인 규칙으로 통일한다.
2. 편집본/반경/변경 여부를 CourseDraft 같은 객체가 관리하도록 한다.
3. 저장 절차를 담당하는 서비스와 FX 지도 캡처 어댑터를 분리한다.
4. PlannerMap의 경로 조회와 캡처 생명주기를 역할별로 나눈다.
5. map.js의 캡처 모드와 핀/경로 표시를 나누되 기존 인터랙션 회귀 검사를 유지한다.

큰 상속 계층을 새로 만들거나 모든 컨트롤러를 한 번에 재작성할 필요는 없다.
실제 수정할 기능과 연결된 책임부터 한 커밋씩 분리하는 편이 검증하기 쉽다.

## 성능·운영·검증

현재 좋은 점: 사용자 정보/코스 목록 캐시, 선택 이미지 지연 로드와 최대 24개 캐시,
도보 구간 단위 캐시, 비동기 작업 결과의 버전 검사, 가격/출처 스냅샷 보존이다.

성장 시 검토할 부분:
- SavedCourseRepository.findAll은 모든 코스와 장소 스냅샷을 한 번에 읽는다.
  당장 느리다고 측정한 것은 아니지만 코스가 쌓이면 페이지 단위 조회가 필요하다.
- 프리뷰 빠른 선택 전환은 표시 결과를 보호하지만 진행 중 DB 요청을 합치거나 취소하지 않는다.
- 신규 설치는 SQL 적용 범위가 나뉘어 있어 스키마 버전 점검과 복구 안내가 필요하다.
- 실제 MySQL의 장애/권한 부족/재접속, OS 창 종료, GUI 접근성은 일반 H2/FXML 검사와 별도다.

수정 순서 제안:
1. 미저장 종료 보호 + 유효한 기존 이미지 보존.
2. 장소 동일성 통일과 추천 회귀 검사.
3. 제보 미검토 큐 및 실행 환경 충돌 처리.
4. 저장/편집 책임 분리와 문서 갱신.
5. Windows 배율·키보드·네트워크 실패를 포함한 시연 시나리오 최종 점검.

## 후속 수정 상태

사용자 승인 후 다음 항목을 구현했다.
- 창 닫기 요청을 FX 스레드의 미저장 확인으로 연결하고 저장/진행 중 작업 동안 종료를 차단한다.
- 공공 장소 동일성 기준을 후보 검색·지도 전달·선택·저장 검증에 적용한다.
  공공 ID가 서로 다르면 병합하지 않으며 공공 ID 없는 별칭은 공공 레코드를 우선한다.
- 캡처 실패 시 해시가 같은 기존 프리뷰를 유지하고, 내용이 바뀐 이미지만 무효화한다.
- 관리자 제보 화면을 검토 대기 기본/상태 필터/50건 단위 ID 커서 페이지 방식으로 바꾼다.
- README의 관리자 인증·후보 수·상세 카드·저장 상태 설명을 갱신한다.

포트 변경과 큰 구조 개편은 이번 변경 범위에 넣지 않았다.
검증은 OS 창 닫기 이벤트의 FX/EDT 연결, 종료 취소/저장 중 차단, 공공 ID 불일치,
기존 이미지 재사용/내용 변경 무효화, 306건 제보 조회와 실제 FXML 페이지 이동을 포함한다.
